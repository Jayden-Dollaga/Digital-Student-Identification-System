Digital Student Identification System (DSIS) — Project Structure, Status, and Development Roadmap
=================================================================================

This document is the live project tracker and architecture guide for the Digital Student Identification System (DSIS). It records the project history, current issues discovered during real-world testing, the implementation plan, and the to-do list that will guide future work. It also explains the purpose of the major files and folders so a new developer or UI designer can understand the codebase quickly.

1. Project summary
------------------

The project is a Windows-based digital student identification system that combines:
- ESP32 firmware for fingerprint scanning and command handling
- Python desktop software for enrollment, attendance logging, backup/restore, and reporting
- SQLite storage for student and attendance data
- A modular GUI built with CustomTkinter

The current goal is to make the system reliable for real-world testing outside the development computer. That means improving portability, dependency handling, UI responsiveness, and attendance refresh behavior.

2. Repository layout and file purpose
-------------------------------------

The repository is divided into four main areas:
- firmware/: Arduino sketches and ESP32 firmware sources
- python/: desktop application, serial logic, database persistence, and GUI modules
- data/: runtime database, exports, logs, backups, and generated files
- tools/ and tests/: packaging, validation, and build automation helpers

Key folders and their purpose:
- firmware/attendance/: attendance-mode firmware sketch used for live scanning
- firmware/enroll/: enrollment firmware sketch
- firmware/delete/: delete/wipe firmware sketch
- firmware/ESP32_Fingerprint_AllInOne/: bundled all-in-one firmware variant
- python/core/: reusable backend services that do not depend on Tkinter/Qt UI widgets
- python/gui/: the original CustomTkinter desktop app UI
- python/gui_qt/: the newer PySide6 Qt UI prototype and replacement shell
- python/services/: database backup and Excel export helpers
- tests/: regression tests, demo apps, and GUI exploration harnesses
- tools/: PyInstaller spec, build scripts, and validation helpers

Key files and their purpose:
- python/main.py: legacy entry point for the serial/CLI workflow
- python/config.py: environment-aware application configuration and runtime defaults
- python/core/database.py: SQLite schema, CRUD, backups, and report queries
- python/core/serial_handler.py: ESP32 connection, read/write, and reconnect behavior
- python/core/attendance.py: attendance event parsing and cooldown filtering
- python/core/firmware_helper.py: firmware discovery and esptool-based upload support
- python/gui/app.py: main legacy GUI controller and page coordinator
- python/gui_qt/main_window.py: main Qt shell and page switching controller
- python/gui_qt/pages/*.py: page implementations for dashboard, attendance, students, logs, reports, and settings
- python/gui_qt/workers/serial_worker.py: background worker for ESP32 polling and scan parsing
- python/settings_store.py: JSON-based settings persistence
- run_qt_gui.py: repo-root launcher for the Qt UI

3. Project history from the start
--------------------------------

The system has evolved in stages:
1. Initial prototype for fingerprint enrollment and scanning.
2. Integration of ESP32 firmware and serial communication with the host computer.
3. Development of a desktop GUI for easier operation.
4. Addition of SQLite-based student and attendance storage.
5. Addition of backup/restore, reports, and role-based access.
6. Refactoring of the GUI into page-based modules for maintainability.
7. Current phase: portable deployment and field-testing hardening.

3. Current issues discovered during real-world testing
-----------------------------------------------------

The following issues were identified during school testing on another computer:
- Dependencies listed in requirements.txt were not always installed completely on the target machine.
- The UI felt laggy on lower-spec machines compared with the developer PC.
- Attendance updates did not always refresh immediately after a scan.
- Some attendance entries appeared out of order or did not move to the top as expected after a registered fingerprint was scanned again.
- The wipe/delete workflow needs clearer integration with database records so the system behaves consistently.
- The start-scan action should not trigger enrollment behavior accidentally.

4. Current implementation focus
------------------------------

The project is currently focused on the following areas:
- Portable deployment for USB-based testing
- Dependency reliability on clean Windows machines
- UI responsiveness and performance optimization
- Attendance refresh reliability
- Real-world validation and bug tracking

5. Phased roadmap
-----------------

Phase 1 — Portable Deployment (Highest Priority)
- [ ] Package the application with PyInstaller
- [ ] Bundle a Python runtime if needed
- [ ] Include all required Python modules inside the portable package
- [ ] Verify the application launches without a separate Python installation
- [ ] Create one-click executable entry point for USB testing
- [ ] Test launching directly from a removable drive

Phase 2 — Dependency Reliability
- [ ] Audit requirements.txt
- [ ] Remove unused dependencies if needed
- [ ] Add any missing required packages
- [ ] Verify startup on a clean Windows installation
- [ ] Create an automatic dependency checker or bootstrap script
- [ ] Add portable runtime validation for deployment machines

Phase 3 — Performance Optimization
- [ ] Reduce unnecessary UI redraws
- [ ] Optimize widget creation and page loading
- [ ] Lazy-load heavy pages where possible
- [ ] Cache statistics or repeated queries
- [ ] Measure startup time and responsiveness on lower-spec hardware

Phase 4 — Attendance Reliability
- [ ] Investigate missed UI refreshes after scanning
- [ ] Improve attendance refresh logic
- [ ] Add a fallback refresh mechanism when the main refresh path fails
- [ ] Verify serial communication recovery after interruptions
- [ ] Test long scan sessions and repeated fingerprint checks

Phase 5 — Real-World Testing
- [ ] Test on another Windows computer
- [ ] Test startup and first-run behavior
- [ ] Test COM port auto-detection
- [ ] Test enrollment workflows
- [ ] Test attendance logging and refresh behavior
- [ ] Test reports, backups, and restore
- [ ] Test unknown fingerprint handling
- [ ] Record all issues discovered during field tests

Phase 6 — Documentation
- [ ] Update README with deployment and testing instructions
- [ ] Create INSTALLATION.md for setup guidance
- [ ] Create PORTABLE_BUILD.md for USB deployment steps
- [ ] Add a troubleshooting guide for common issues
- [ ] Document hardware requirements and known limitations

Phase 7 — Release Candidate
- [ ] Build Release Candidate 1 (RC1)
- [ ] Package all deployment files together
- [ ] Version the release clearly
- [ ] Keep a rollback copy of the last known-good build
- [ ] Publish a GitHub release if appropriate
- [ ] Prepare a demonstration package for school testing

-------------------------

1. Build a portable deployment workflow using PyInstaller or a similar packaging tool.
2. Create a reliable dependency bootstrap script for Windows.

8. Important notes
------------------

- The current priority is real-world reliability over new features.
- The team should treat every field test as a bug-reporting session.
- The portable build should be tested as if it were being used by a teacher or staff member with no Python setup experience.
- Any change that affects attendance flow or data deletion should be tested carefully before release.
